## 0. 一句话摘要

ww-job 在连续 11 档负载（P1~P11）下验证了**正确性红线全绿**（触发不丢、不重、SINGLE 防重叠、admin/executor 宕机不悬空），并坐实了一条**清晰的性能瓶颈链**：每触发 1 次任务要写 3 次独立事务、约 10 次 DB 往返（调度写放大），这个放大倍数让 binlog fsync → redo-log fsync → 连接池 → 触发线程池 → 共享 DB 行锁**轮番当墙**，单 admin 快任务吞吐封顶 ~150/s，双 admin 不扩展（~142/s）。慢任务是另一类独立的墙（执行器 24 线程 ÷ 任务时长 ≈ 12/s）。测试还挖出并验证修复了 1 个真实竞态缺陷（F6-2），另确认 1 个缺陷**仍待修**（F2-9 stop 复活）。

## 1. 指标口径：先分清「执行耗时」与「调度延迟」

### 1.1 为什么必须区分

`job_log.trigger_time / handle_time` 是**秒精度 DATETIME**：同一秒内完成的任务两者差 = 0ms，跨秒才显示 1000ms。因此**秒级日志读不出"真实执行耗时"**，只能读"这任务花了多少秒边界"。若不区分，会得出两个错误结论：把 ~6% 的"1000ms"行当成执行慢（实际是调度延迟上界），或漏掉慢任务的真实排队。

### 1.2 一条触发的生命周期（延迟解剖）

```
cron 到点 ──► 时间轮 (故意 +1s TICK_MS，保证永不提前) ──► claim (selectByIdForUpdate 行锁 + next_time 推进，2 次往返)
        ──► decide (行锁 + countRunning + 插 job_log 事务，3 次往返) ──► dispatch (route + selectById，2~3 次往返)
        ──► HTTP POST /run ──► executor 线程池排队 ──► handler 执行 ──► 回调收账 (updateById，2 次往返)
```

| 段 | 归属 | 实测/设计依据 |
| --- | --- | --- |
| 时间轮 +1 tick（≤1s） | **调度延迟** | `ScheduleHelper.java:99` +TICK_MS，"宁可晚不可早"的防跳拍设计 |
| claim/decide/dispatch 的 DB 往返 | **调度延迟** | 每触发 ~10 次往返，F2-8 |
| 同 job 高频触发行锁排队（~200ms/触发） | **调度延迟** | 实测 P7a vs P7b，F5-1 |
| HTTP 分发 connect 3s / read 10s | **调度延迟** | 触发无界，仅超时进 status=3 |
| executor 线程池排队（慢任务挤压快任务） | **调度延迟（执行层排队）** | F4-1/F4-2，cross-second 实证 |
| handler 本身运行 | **执行耗时** | 快任务 <5ms（handler 内计时）；慢任务 ≈ param 值 |

**结论：报告里所有"1000ms / P99"一律指调度延迟上界，快任务执行耗时本身 <5ms；慢任务的执行耗时是可预期的 param 秒数，观测它的正确指标是"同时运行数"而非 P99。**

### 1.3 全报告健康指标速查

| 指标 | 用什么测 | 对应什么 |
| --- | --- | --- |
| 触发密度（实际/s） | 冻结态 job_log 计数 ÷ 窗口秒数 | 调度吞吐，与配置 D 对比看欠账 |
| distinct job_id | 冻结态去重 | **触发不丢**（= N 才合格） |
| status 分布 {0/1/2/3} | 冻结态统计 | 0=执行中残留（故障信号）、1=成功、2=明确失败、3=未知/被防重丢弃 |
| cross-second %（handle≠trigger） | 秒级对拍 | 队头阻塞/调度排队量化（纯快基线 5.1%，混合 27.9%） |
| 同时运行数（status=0 峰值） | 冻结态或采样 | 慢任务并发上限（比 P99 可靠） |
| 空秒数 / per-job interval | 秒分布 | 调度健康；间隔被拉长=任务"少跑"，是容量欠账而非丢任务 |

> 判读纪律：**窗口统计一律在 drain 冻结后跑**——负载进行中跑 OFFSET 分页会因并发插入分页漂移，总量虚高 19~21%（F4-4）。

## 4. 逐 Phase：实测数据、发现、结论

### 4.1 Phase 1 基线 D=10（零负载参照）

- **实测**：密度恒 10.1/s、1838 条全 status=1、零空秒、distinct=100；admin CPU 13% 单核 / 236MB，executor 1.7% / 144MB。
- **发现**：P99「~1000ms」= **调度延迟上界**（+TICK_MS 故意晚 ≤1s + 秒精度取整），快任务执行 <5ms（F1-1）。时间边界必须显式对齐容器 UTC（F1-2）；P99 秒精度量化陷阱在慢任务维度不可靠（F1-3）。
- **结论**：D=10 系统无压力，确立零负载基线，正确性红线全绿。

### 4.2 Phase 2 阶梯递增 D=50/100/300 + A/B（快任务，找调度吞吐拐点）

**D=50（第一档，默认双 fsync）**
- **实测**：50→30/s 稳定；8583 条全 status=1；每任务触发间隔被拉长到 14.5~19s（配 10s）；admin CPU 仅 37% 单核；MySQL 持续 `waiting for handler commit`。
- **发现（F2-1）**：mysql:8 默认 `innodb_flush_log_at_trx_commit=1 + sync_binlog=1` → 每次 commit 双 fsync（redo+binlog）；每触发 ≥3 次独立 commit → ~6 fsync/触发；WSL2 虚拟磁盘 fsync 慢 → commit 成吞吐瓶颈，**~30/s ≈ fsync 容量上界（30/s × 6 ≈ 180 fsync/s）**。属环境 × 设计叠加，非 CPU。
- **A/B 验证（F2-2）**：只翻转 `sync_binlog=0`，密度 30→50/s 恢复、3min 稳定、正确性全绿、job 132 的 +10/+20 跳边界消失 → 墙是 binlog fsync 而非 CPU/线程池。附带：接近容量时有 3 个整秒空档（整批落下一秒，无 status=3，F2-3）。
- **结论**：D=50 已是默认配置下的拐点；此档起环境改为 `sync_binlog=0` 继续找下一道墙。

**D=100（第二档）**
- **实测**：~100→88/s 稳住（整窗 95.1/s）；17220 条全 status=1、零空秒；admin CPU 141% 单核；processlist 再现 `waiting for handler commit`（回调更新）。
- **发现（F2-6）**：去掉 binlog fsync 后 `flush_log_at_trx_commit=1` 的 **redo-log fsync 成为第二道墙**（~285 commit/s 逼近 fsync 容量）。
- **结论**：`sync_binlog=0 + flush_log=1` 下 soft ceiling ~88-95/s。想继续找 CPU/线程池上限需连 redo fsync 也关（重启容器）。

**D=300（第三档，双 fsync 全关）**
- **实测**：稳态封顶 ~120/s（只交付 40%）、21747 条全 status=1、distinct=3000、零空秒；**每任务触发间隔 p50=22s/p90=31s**（每个任务都"少跑"）；admin CPU 177% 单核；jstack 触发线程池 24 个仅 ~9 RUNNABLE（未饱和）；DB 无 fsync。
- **发现（F2-8）**：第三道墙不是 CPU/线程池，而是 **HikariCP 默认连接池 10 × 写放大**——快任务每触发 **~10 次 DB 往返**（claim 2 + select 1 + decide 事务 3 + dispatch select 1 + route ~1-2 + dispatchOne update 2），10 连接 ÷ (10×~8ms) ≈ 125/s ≈ 实测 118/s 严丝合缝。
- **结论**：瓶颈链 = binlog fsync(~30) → redo fsync(~88-95) → **连接池 10×往返(~120/s)**；代价全部由"触发频率被拉长"承担，正确性全程无损。

**A/B：pool 10→30（单变量验证 F2-8）**
- **实测**：密度 120→**150/s**（+25%，全窗 149.6/s）；status {1:26917, 3:164}、status3=0.6%（首次破零，见下）；admin CPU 177→263%；**jstack 24/24 触发线程全 RUNNABLE**（已饱和）。
- **发现（F2-8 修订 + F2-10）**：池放大 → 密度跟涨 → **连接池墙坐实**；池不再饱和后**新墙 = 触发线程池 24**（`ScheduleHelper` 硬编码 `max(4, cores×2)=24`，**不可配置**；24 线程 × ~150ms/触发 ≈ 160/s ≈ 实测）。0.6% status=3 = 个别任务回调 >10s 时下一次触发被 SINGLE 防重丢弃（主动防重非丢任务）。
- **结论**：要突破 ~150/s 需产品改造（线程池可配化 + 可能再加连接池），写放大仍是统一根因。

### 4.3 Phase 3 最大同时运行任务数（全慢任务 param=2s，换维度）

- **实测**：D=50 → 成功吞吐 **12.1/s**、status {2:63.5%, 1:23.5%, 3:13.0%}、running 峰值 147；D=100 → 成功吞吐 **12.7/s**、status {2:81.5%, 1:11.8%, 3:6.7%}、峰值 157；admin CPU 全程 4~10% 单核（几乎空闲）。
- **发现（F3-1/F3-2）**：执行器墙**平直**——`ExecutorAutoConfiguration` 硬编码 `ThreadPoolExecutor(12, 24, ArrayBlockingQueue(100), AbortPolicy)`，**持续成功吞吐 = 24 线程 ÷ 2s ≈ 12/s，与 D 无关**；超出部分全被 AbortPolicy 拒绝（status=2），拒绝率随 D 涨而成功吞吐钉死。status=3 达 13% = 队列积压致回调 >10s → 下一次触发被 SINGLE 防重静默丢弃，**自我放大**。
- **结论**：调度平台容量 = 负载画像的函数，两类墙独立——**快任务受 admin 写放大（~150/s）限制，慢任务受执行器 线程数÷任务时长（24/T）限制**。

### 4.4 Phase 4 混合任务 + 失败场景

- **实测（Test A 70/20/10）**：密度 162/s、status {1:60.5%, 2:39.4%, 3:0}、成功吞吐 **98.2/s**、**cross-second 27.9%**、max_running 148。
- **实测（Test B 95%快+5%fail）**：密度 153/s、status {1:95.3%, 2:4.7%}、成功吞吐 **145.9/s**、cross-second 5.1%；150 个 fail 任务全按预期 status=2；**job_alert_state=0**（1385 次失败零告警）。
- **发现**：混入 30% 慢任务 → 吞吐 145.9→98.2/s（**-33%**），cross-second 5.1%→27.9%——慢任务霸占 24 执行器线程、快任务在队列里被连带拖慢（**队头阻塞，F4-1**）；cross-second 是队头阻塞的最便宜量化指标（F4-2）。失败链路端到端正确，但告警对空 alarmConfig 完全静默（F4-3）。
- **结论**：混合负载共享池是融合墙（成功吞吐 = 24 ÷ 加权平均时长），混合部署是最差画像；告警链路存在可见性缺口。

### 4.5 Phase 5 并发手动触发（SINGLE 互斥）

- **实测**：100×同 job（param=2s，停用）→ job_log = **{1:1, 3:99}**（精确 1 分发 + 99 阻塞）；per-req avg 334ms/p95 567ms。100 个不同 job 各 1 次 → {1:100, 3:0}；per-req avg 131ms/p95 182ms。
- **发现（F5-1）**：SINGLE「防重叠」语义在极端并发下精确成立、**无任何重复执行**。代价 = `decide()` 的 `selectByIdForUpdate` 行锁将**同一 job 的高频触发串行排队**（同 vs 异 job 差 ~200ms/触发 = 锁等待），粒度 **per-job**（多任务互不干扰）。
- **结论**：SINGLE 用"锁换正确性"，取舍合理；接口调用方需知悉同 job 超高并发会线性吃锁延迟。附带确认 F3-2 机制在生产路径复现（执行 > cron 间隔 → 一半触发被防重丢）。

### 4.6 Phase 6 双 admin 集群对照（P8a 修复前 / P8b 修复后）

- **实测（P8a 双 admin）**：D=300 纯快，**142.5/s**；status {1:99.88%, 3:33 条(0.12%)}；distinct=3000；两台 admin 均 <1 核未饱和；MySQL 60 连接。
- **发现**：**双 admin ≈ 单 admin（142.5 vs 149.6/s）不扩展**（F6-1）——触发线程 24→48、连接池 30→60、CPU 未饱和，吞吐纹丝不动，墙在**共享 DB 行锁串行化**（claimNextTime/decide 的 `FOR UPDATE`，`Innodb_row_lock_waits` 稳态 ~85 次/s，单 admin 趋近 0）。33 条 status=3 全为**同秒双 claim 竞态**（F6-2）：胜者把落后点推进到相邻秒边界，败者毫秒内拿锁误判边界可 claim → 连发；SINGLE 兜住无重复执行，但**非 SINGLE 任务 = 毫秒级连发两次的真实重复执行风险**。
- **实测（P8b 修复后，commit 44e0b16 秒级截断）**：**127.0/s、status 全 {1}、status=3 = 0**（33→0）、distinct=3000；决定性 SQL（同秒双触发）返回 0。密度 -11% 经 P9 反证为短窗采样方差、非修复代价（per-job interval 未变）。
- **结论**：F6-2 竞态修复验证通过且无吞吐代价；双 admin 扩展的正确路径是**分片/CAS 去锁**（详见 §6）。

### 4.7 Phase 7 30 分钟稳定性（P9）

- **实测**：同一批次连跑 31min55s，**278360 行 / 145.4/s**，status 全 {1}、**status=3 全程 0**、distinct=3000、1915/1915 秒无空秒；线程数 A=85/B=74 全程恒定；MySQL 连接 59~62 恒定；堆 71~87% 震荡有界；YGC ~50 次/分恒定、**FGC 全程 0**。
- **发现（F7-1/F7-2）**：F6-2 修复 30min 零复发（修复前 3min 就有 33）；30min 均密度 145.4/s **高于** P8b 的 127.0/s → 坐实 P8b 的 -11% 是采样方差。无线程泄漏、无连接耗尽、无 GC 异常、无随时间退化。
- **结论**：该配置（双 admin + 共享 DB 饱和）可持续无故障长跑，调度正确性与进程健康双达标。

### 4.8 Phase 8 admin 强杀故障恢复（P10）

- **实测**：饱和稳态 taskkill /F admin A(8080)，B 单机接管 235s。**pre-kill 22216 行/131.5/s、post-kill 33485 行/142.5/s，两窗 status 全 {1}、distinct 全 3000**；drain 后全局 status=0 残留 = 0；executor registry 全程在线。
- **发现**：**executor 侧 failover 零丢失**（F8-1：A 的 in-flight 分发全部经 B 收回调，无一条残留 status=0）；**B 单机接管密度反超** 142.5 ≥ 131.5/s（F8-2：双 admin 的行锁竞争税随 A 死消失，呼应 F6-1）；claim-未投递点随进程消亡丢一拍是**瞬态自愈**非故障（F8-3，distinct 3000→2986→3000）。
- **结论**：admin 单点死亡场景被回调 failover 完全收口，巡检兜底无需介入。**部署注意（F8-4）**：巡检 SQL 用 MySQL `NOW()` 比 JVM 写入时间，若 DB 会话时区 ≠ JVM 时区，60s 巡检会静默退化成 ~8h。

### 4.9 Phase 9 executor 强杀故障恢复（P11）

- **实测**：双 admin 存活下 kill executor，对停用 batch **手动触发 91 次分四窗**，executor 离线 5.7min，全局残留 status=0 = 0：

| 窗 | 触发 | 落账 |
| --- | --- | --- |
| 基线 executor 在线 | id 1 | status=1 |
| 死·registry 未清 | id 11-40（30） | 全 status=2 handle_code=500「Connection refused」，2.1s 落账 |
| RegistryCleaner 下线（最后心跳+92s） | — | registry 行移除 |
| 死·registry 已空 | id 51-80（30） | 全 status=2 handle_code=NULL「无可用执行器」 |
| 重启（boot 2.0s 自动重注册） | id 91-120（30） | 全 status=1，恢复 |

- **发现**：dispatch 到死 executor = **快速明确失败不悬空**（F9-1：connection refused 允许重试 → status=2，只有超时才 status=3 防重复）；**两相落账可区分**（F9-2：500+I/O error = 宕机未感知 vs NULL = 已下线）；RegistryCleaner 90s 端到端移除实测（F9-3）；重启 2s 零人工恢复（F9-4）。
- **结论**：executor 宕机不会产生 status=0 孤儿。**唯一未覆盖**：ack 后 executor 中途崩溃（job 已受理、回调永不达）→ 该 status=0 孤儿本应由 60s 巡检兜底收 status=3，但本环境巡检时区错位无法窗口内实测（需时区一致的部署环境验证，见 §7）。

## 5. 横切结论（跨 Phase 串起来的判断）

### 5.1 正确性红线：全部通过

| 主张 | 证据 | 结论 |
| --- | --- | --- |
| 触发不丢 | 各饱和档 distinct=任务数 | ✅ 无静默丢任务 |
| 不重复执行 | P7a 100×同job → 1+99；P8b 决定性 SQL=0 | ✅ SINGLE 精确、F6-2 竞态已消 |
| 失败端到端 | P6b 5%fail → status=2 全对 | ✅ |
| executor 宕机不悬空 | P11 四窗零 status=0 孤儿 | ✅ |
| admin 死零丢失 | P10 pre/post 全 status=1 | ✅ |
| 巡检兜底（ack 后崩溃） | 机制早前 timeout 场景验证过 | ⚠️ 时区对齐环境才能窗口内闭环 |

### 5.2 瓶颈链：同一根因（调度写放大）换着方式当墙

```
binlog fsync    → ~30/s    (F2-1, 默认持久化第一道墙)
redo-log fsync  → ~88-95/s (F2-6)
连接池 10 × 往返 → ~120/s   (F2-8)
触发线程池 24    → ~150/s   (F2-8修订, 单 admin 当前墙)
共享 DB 行锁     → ~142/s   (F6-1, 双 admin 墙)
```

**统一根因 = 每触发 3 次独立事务 commit（job_log 插 / next_time 更新 / 回调更新）+ ~10 次 DB 往返的调度写放大。** 这是 ww-job 最核心的性能话题：调参只能在同一道墙内挪动，突破需产品改造（见 §6 第二优先级）。

### 5.3 扩展性：纵向往 admin 加实例无效

双 admin ≈ 单 admin（142.5 vs 149.6/s），触发线程/连接池翻倍而吞吐不动 → 墙在共享 DB 行锁。横向扩展需按 job 分片或 CAS claim（§6-P3）。

### 5.4 稳定性与资源健康：达标

P9 三零（status3/泄漏/FGC）+ 连接/堆有界，可长时间跑。

### 5.5 故障恢复：闭环，边界诚实标注

| 场景 | 行为 | 状态 |
| --- | --- | --- |
| admin 强杀 | 回调 failover 零丢失、单机接管反超 | ✅ 实测 |
| executor 强杀（dispatch 侧） | status=2 快速失败、90s 下线、2s 恢复 | ✅ 实测 |
| executor ack 后崩溃（回调侧） | 应靠 60s 巡检兜底 status=3 | ⚠️ 待时区一致环境验证 |

### 5.6 容量参考（单机、未调优、仅供参考）

| 形态 | 吞吐 | 墙 |
| --- | --- | --- |
| 单 admin 快任务（pool=30） | ~150/s | 触发线程池 24 |
| 双 admin 快任务 | ~145/s | 共享 DB 行锁 |
| 默认持久化（双 fsync）单 admin | ~30/s | binlog fsync（先定持久化级别再谈容量） |

## 6. 优化方向（按优先级，附预期收益）

### 🥇 第一优先级：可靠性缺陷（建议先修）

**R1. 修复 F2-9 stop「复活」（当前未修复，压测 drain 反复现）**
- 问题：高负载下 `/job/{id}/stop` 置 triggerStatus=0 后，in-flight 触发用 `trigger()` 早期加载的旧实体整写回 `updateById(job)`（`JobTriggerServiceImpl.java:75/131/183`），把 stop 覆盖回 1 → 任务复活。实测档间清理 iter2 仍见 25~58 个复活。
- 修法：写回改为只更新目标列（`LambdaUpdateWrapper` / `UpdateWrapper`，杜绝整实体覆盖），或加 `UPDATE ... WHERE id=? AND trigger_status=1` 条件让 stop 后的写回 0 行落空。
- **预期收益**：stop 语义可靠，消除"已停任务继续跑"的操作事故与压测清理成本（档间不用再循环验到 0）；代码改动小、风险低。

**R2. stop 接口静默失败（顺带 R1 处理）**
- 问题：`/stop` 无条件置 0 且永远返回 success()，响应码无法检出真实失败；loadgen stop 曾静默漏停 1 个任务（F2-4）。
- 修法：stop 按实际影响行数/状态返回，前端可感知"该任务本来就没在跑"或失败。
- **预期收益**：运维/自动化可校验 stop 结果，避免静默状态错乱。

### 🥈 第二优先级：性能杠杆（写放大是核心，改造收益最大）

**P1. 压缩每触发的 DB 往返与事务数（最高杠杆）**
- 问题：每触发 ~10 次 DB 往返、3 次独立事务 commit。这是瓶颈链每道墙的公共分母（F2-8/F2-6/F2-1）。
- 修法：① 合并/减少调度路径事务（decide 与 job_log 插入、claim 与 next_time 更新尽量单事务）；② 去冗余 selectById（job 已在手的不再重查）；③ 回调更新改条件 UPDATE（`UPDATE job_log SET status=? WHERE id=? AND status=0`）减少读。
- **预期收益**：往返从 ~10 压到 ~4-6，连接池墙、触发池墙同步后移——按 P4b 的线性关系（10 连接 ÷ 往返数），单 admin 吞吐有望从 150/s 翻倍级上探。**这是访谈上"你如何定位并压榨调度平台性能"的核心答案**。

**P2. 触发线程池可配化（顺带 HikariCP 参数进配置）**
- 问题：`ScheduleHelper` 硬编码 `max(4, cores×2)=24`，当前单 admin 的最终墙（F2-8修订）；连接池默认 10 已是历史包袱（F2-8）。
- 修法：把触发线程池核心/最大/队列、连接池大小暴露为 `application.yml` 配置项。
- **预期收益**：单 admin 150/s 上探；且给运维按机器规格调参的能力。**注意**：放大后新墙在哪未测（见 §7-G2），配置化是放开天花的必要非充分条件。

**P3. 双 admin 扩展：按 job 分片 或 CAS claim**
- 问题：双 admin 不扩展，墙 = 共享 DB `FOR UPDATE` 行锁串行化，稳态 ~85 次/s 败者等待（F6-1）。
- 修法：① 按 job 分片——每 admin 只 claim 分配给自己的 job_id 集合，败者等待归零；② claim 改 CAS：`UPDATE job_info SET next_time=? WHERE id=? AND next_time=旧值`（0 行受影响即放弃），从根上消除"读-判-写"竞态（比 F6-2 秒截断更彻底）。
- **预期收益**：加 admin 实例才可能带来吞吐收益；CAS 顺带根治 F6-2 一类竞态的残余边界。

### 🥉 第三优先级：容量规划与产品体验（低成本、可立即做）

**C1. 慢任务隔离（专用执行器/分组）**
- 问题：所有 handler 共池 → 30% 慢任务让整体吞吐 -33%（F4-1）。
- 修法：建任务时选执行器分组/建议慢任务放独立 executor 实例。
- **预期收益**：混合负载 98→~146/s，快任务不再被慢任务拖 P99。

**C2. SINGLE 防重可见化 + 建号提示**
- 问题：status=3「被防重丢弃」在慢任务高密度下达 13%，日志/前端静默（F3-2）。
- 修法：状态页把"被防重丢弃"与"真实失败"分开展示；创建 cron 间隔 < 预计执行时长的任务时提示。
- **预期收益**：用户不再"以为在跑实际没跑"，降低对平台的误判。

**C3. 告警链路可见性**
- 问题：未配 alarmConfig 的任务失败零告警、监控页无记录（F4-3，1385 次失败 job_alert_state=0）。
- 修法：跳过时打审计日志，或详情展示「已告警 / 未告警（未配置告警人）」。
- **预期收益**：运维可信监控，故障有据可查。

**C4. 部署时区一致性（配置敏感项，非 bug）**
- 问题：DB 会话时区 ≠ JVM 时区时，60s 巡检静默退化成 ~8h（F8-4）。
- 修法：部署文档强约束 DB 时区与 JVM 一致；或巡检 SQL 显式用与写入一致的时区。
- **预期收益**：status=3「执行超时未知」兜底在真实环境闭环，故障恢复不留死角。

**D（工具/方法论，低成本）**：压测工具分页改游标式（F4-4）；档间清理改"停全量→等 5s→重扫验 0"已内置（loadgen.py cmd_stop）。
